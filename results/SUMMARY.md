# E1 — what one kind of fault makes each framework do (summary)

Raw data: `results/e1/<row>/<mode>/` (`server.jsonl` = fake server's log, source of truth; `client.txt` = client
stdout/stderr + exit + wall time; `counter.txt` = one line per tool execution). Every cell: `results/e1/TABLE.md`
(generated by `harness/e1_summarize.py`, also `results/e1/cells.json`). Versions: `results/e1/VERSIONS.txt`.

Method in one paragraph: one fake OpenAI-compatible server per cell (`harness/fault_server.py`), one framework run
per cell in its **default configuration** (only base URL, dummy key, model name and telemetry/tracing off were set;
`harness/e1_client.py`), a single `counter` tool. The fault is applied to *every* request it targets, so a cell counts
all requests until the framework gives up. Cap 25 min per cell. **No wait constant was shrunk anywhere in E1**:
every wall time below is with defaults. Rows run non-streaming; streaming rows (`*-stream`) were run for the
drop modes only.

## Findings (each with its evidence)

1. **CrewAI executes the tool again for every agent-level retry: 3 executions for one persistent fault.**
   *Round 2: this is already reported upstream — crewAIInc/crewAI#5802 (open, opened 2026-05-14), fix PRs #5822 and
   #6048 (open). Not a new finding; see REPORT.md "Round 2" for the verified repro, line-pinned sources and workaround.*
   `Agent.max_retry_limit` defaults to 2 and a retry re-enters `execute_task` from the task prompt, so the model is
   asked again *without* the earlier tool result and the tool runs again. Evidence: `results/e1/crewai/after-tool-500/`
   (`counter.txt` 3 lines at 3.1 s, 4.6 s, 6.0 s; `server.jsonl` shows 3 × [tool call, 3 × 500]),
   `crewai/after-tool-drop/`, `crewai-stream/after-tool-drop-chunked/`; source: crewai 1.15.28
   `crewai/agent/core.py` (`max_retry_limit` default=2; `_handle_execution_error` → `execute_task`).
   Caveat: the fake model re-issues the tool call whenever a request lacks the tool result; a real model given the
   same prompt again very likely does the same, but that is an assumption.
2. **CrewAI stacks three retry layers: 3 (OpenAI SDK) × 3 (CrewAI LLM rate-limit retry) × 3 (agent retry) = 27
   requests for a 429.** The middle layer (`crewai/llms/retry.py`, 3 attempts, 1 s/2 s ±20 %) classifies by status
   429 *or* the text "rate limit", so a 500 saying "Rate limit reached" also gives 27; a neutral 500 gives 9
   (3 × 1 × 3). It tries to read Retry-After only from dict-shaped headers; on OpenAI SDK exceptions the measured outer
   gaps are 1.0–1.3 s then 1.7–2.4 s (its own backoff), i.e. Retry-After not honored by that layer; a quota 429 with
   Retry-After 3600 is still retried 9 times. Evidence: `crewai/429`, `crewai/429-hard`, `crewai/500-*`.
3. **smolagents: the outer retry decision depends on error text, in both directions, and on which model class is used.**
   - Unrelated 500 whose text contains "429" (`req_4291ab`, `14290 tokens`): 9 requests, 621 s (OpenAI) / 500 s
     (LiteLLM) before the error, vs 3 requests in ~1.3 s for a neutral 500. Evidence: `smol-*/500-text-429`, `smol-*/500-neutral`.
   - Real 429 with a neutral body: OpenAIServerModel retries it (the SDK's text "Error code: 429" matches) → 9, 1066 s;
     LiteLLMModel does **not** (LiteLLM's text "litellm.RateLimitError: RateLimitError: OpenAIException - Slow down,
     please." contains none of "429", "rate limit", "rate_limit", "too many requests") → 3. Evidence: `smol-*/429-neutral-body`
     (exception text in `client.txt`).
   - Quota exhausted (insufficient_quota, Retry-After 3600): the OpenAI SDK correctly refuses to retry (Retry-After above its `MAX_RETRY_AFTER_DELAY` = 120 s; Round 1 said 60 s, corrected in Round 2),
     smolagents' outer loop retries anyway → 3 requests, 591 s before the error surfaces. Evidence: `smol-openai/429-hard`.
   - Outer gaps measured (s): 142–232 before the 2nd outer attempt, consistent with 60·2·(1+U) = 120–240 s; total
     time to error 500–1066 s, consistent with TASKS.md's 6–20 min. Retry-After 1 is ignored by the outer layer.
4. **Every OpenAI-SDK-based stack honors Retry-After at the SDK layer**: SDK retry gaps are 1.00–1.06 s for 429 with
   Retry-After 1 vs 0.38–1.0 s jittered backoff for 500s; with Retry-After 3600 the SDK does not retry at all
   (1 request). Evidence: `inner_gaps` in `results/e1/cells.json` for all `*/429`, `*/500-neutral`, `*/429-hard`.
5. **LangGraph (langchain-openai 1.7.2) has no request timeout by default**: one request held by a silent server for
   the whole 25-min cap, no retry, no error. `ChatOpenAI.request_timeout` defaults to `None` and is passed to the
   OpenAI client as `timeout=None`. All other rows time out at 600.0–600.1 s and retry twice (3 × 600 s = 30 min
   to error, not reached within the cap). Evidence: `*/timeout/server.jsonl` (`client_closed_held_connection` events
   600 s apart; LangGraph: one close at 1500 s = the cap kill).
6. **Mid-stream drops are not retried by any SDK layer** (1 request; streaming errors surface after a 200), except
   CrewAI's agent retry (3) and smolagents' step loop (below). Evidence: `*-stream/drop-chunked`.
7. **Close-delimited stream truncation is accepted as a successful answer** by Agents SDK chat, LangGraph, CrewAI,
   Pydantic AI and ADK (final output `'Do'`, no error); Agents SDK responses raises `ModelBehaviorError`; smolagents
   loops 20 steps (23 requests) and returns an error string as its final answer. Qualification: in this mode the
   server closes a response that had no Content-Length or chunked framing, which HTTP treats as a legal end of body;
   only the missing `finish_reason`/`[DONE]` shows the truncation. With chunked framing (as real API servers send),
   every framework raises. Evidence: `*-stream/drop` vs `*-stream/drop-chunked`.
8. **No framework other than CrewAI re-executed a tool** in any cell (E0 result reproduced with default retry settings;
   E0 itself ran with `max_retries=0`, see REPORT.md). Evidence: `counter.txt` across `results/e1/*/after-tool-*`.

## CrewAI: what the patch actually changes — `results/e3/crewai-before` vs `crewai-after`
Same harness, same fault server, CrewAI 1.15.28 source at base commit `dec075b5` (before) and at the
branch head (after). Default CrewAI configuration in both runs; `Retry-After: 1` on the 429 cell.

| mode | before patch | after patch |
|---|---|---|
| 429 (Retry-After: 1) | 27 chat requests (`retry_count_hdr` 0 ×9, 1 ×9, 2 ×9) | **15** (0 ×9, 1 ×3, 2 ×3) |
| 500-neutral | 9 chat requests (0 ×3, 1 ×3, 2 ×3) | 9 (unchanged) |

The 15 is not a formula: it is the request count in the server log. The first attempt keeps the SDK's own
retries (three attempts, `retry_count_hdr` 0/1/2), and the two rate-limit replays CrewAI makes now send one
request each instead of three. 500 is untouched because CrewAI never replays a 500 at the model layer, so
there is no replay for the SDK's retries to stack on.

Evidence: `results/e3/crewai-before/{429,500-neutral}/server.jsonl` and `results/e3/crewai-after/{429,500-neutral}/server.jsonl`
(`chat/completions` lines only; `/api/show` and disconnect events excluded).
